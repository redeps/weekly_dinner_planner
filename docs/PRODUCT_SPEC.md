# Product Specification — Meal Planner

Status: Foundation (Milestone 0). This document is the **source of truth**
for the product. Any future implementation work — human or agent — should be
checked against this document before being merged. If code and this document
disagree, this document wins unless a `docs/DECISIONS.md` entry says
otherwise.

## 1. Product Concept

Meal Planner is a small household web application for storing recipes and
generating a weekly dinner plan and matching grocery list.

Core loop:

1. Recipes are saved once, with a few key variables attached.
2. A simple weekly calendar is entered (which days are busy, what time
   dinner needs to be ready).
3. A week plan is generated — one recipe per day — weighted by seasonality
   and rotation (avoiding recent repeats), and respecting busy days by
   preferring quicker recipes.
4. Any day can be swapped for a different recipe.
5. A grocery list is generated from the finished week plan.

## 2. Product Principles

The application should be:

- small
- free-first
- easy to maintain
- mobile-friendly
- visually clean
- photo-friendly
- easy to browse and search
- easy to swap a single day without redoing the whole plan

It must explicitly **not** grow into: full nutrition tracking, calorie
counting, recipe sharing/social features, e-commerce/grocery delivery
integration, complex permissions, or unnecessary frontend frameworks.

This is a useful household tool, not a recipe platform. When in doubt,
choose the smaller, simpler option.

## 3. Initial Technical Architecture

Prototype stack:

- Python
- Streamlit (UI)
- SQLite (database)
- Local filesystem storage for recipe photos
- pytest for testing

Must run entirely inside a GitHub Codespace with no cloud services required.

Potential future architecture (NOT built now — see Milestone 9):

## 5. Recipe Model

Every recipe has:

- `id`
- `name`
- `photo`
- `cook_time_minutes`
- `family_enjoyment` (rating)
- `seasonality` (winter / spring / summer / fall / all-season)
- `is_quick_fallback` (true for near-zero-effort options like frozen pizza
  or takeout — see §8)
- `servings`
- `instructions` (free text, ordered steps)
- `notes`
- `created_at`
- `updated_at`

Ingredients are **not** a text blob on the recipe — they live in a separate
structured table (`recipe_ingredients`, see `docs/DATA_MODEL.md`) so the
grocery list can be generated by aggregation rather than parsed from text.

## 6. Ingredients

Each recipe has zero or more structured ingredient lines:

- name
- quantity
- unit
- store category (produce, dairy, meat, pantry, frozen, other) — used to
  group the generated grocery list for easy transcription

Quick-fallback recipes (§8) may have zero ingredient lines (e.g. "takeout"
needs none).

## 7. Weekly Calendar Input

Before generating a plan, the user enters a simple 7-day calendar:

- for each day: busy (yes/no)
- for each day: dinner-ready time, defaulting to **6:00 PM**, overridable
  per day

This is input only — no recurring calendar sync, no external calendar
integration.

## 8. Prepopulated Quick-Fallback Recipes

The app ships with a handful of seeded recipes flagged
`is_quick_fallback = true` — e.g. fish fingers, frozen pizza, takeout. These:

- have very low `cook_time_minutes`
- typically have no or minimal ingredient lines
- are candidates the generator can lean on for busy days
- are treated as ordinary recipes otherwise (editable, deletable, ratable)
  — the flag is just a signal to the generator, not a separate data model

## 9. Plan Generation

Generating a week plan picks one recipe per day, weighted by:

1. **Seasonality** — recipes tagged for the current season are preferred
   over off-season or all-season recipes are treated as a safe default.
2. **Rotation** — recipes cooked recently (see `last_cooked_at` in
   `docs/DATA_MODEL.md`) are deprioritized, so the same meals don't repeat
   too often. The exact "recently" window (e.g. 3 weeks) is configurable
   and recorded in `docs/DECISIONS.md` once chosen.
3. **Busy days** — on days marked busy, or where the dinner-ready time is
   tight, recipes with lower `cook_time_minutes` (including quick-fallback
   recipes) are preferred.
4. **Family enjoyment** — higher-rated recipes are preferred, as a
   tie-breaker among otherwise similar candidates.

This is a **weighted random / scoring approach, not a strict optimizer** —
see `docs/AGENT_INSTRUCTIONS.md` for the principle of keeping this simple
rather than building a full constraint solver.

## 10. Editing a Generated Plan

Once a week plan is generated:

- each day is individually viewable (clicking a day shows the full recipe:
  photo, ingredients, instructions)
- each day can be swapped independently for a different recipe, without
  regenerating the rest of the week
- swapping a day updates the grocery list automatically

## 11. Grocery List

Generated from the finished week plan by aggregating ingredient lines across
all seven days' recipes (summing quantities where units match).

- grouped by store category for easy transcription
- **not** designed for use inside a store — no check-off state, no mobile
  "shopping mode." The user transcribes it to a handwritten list. Keep this
  screen simple: a clean, printable/readable list, nothing more.

## 12. History

Each time a plan is finalized (or a day is confirmed as cooked), the app
records which recipe was cooked on which date. This powers the rotation
weighting in §9 and gives a simple "what have we cooked lately" view.

**Critical implementation rule:** history/last-cooked records must be
created only by business-logic operations (e.g. a `finalize_plan()` or
`mark_day_cooked()` service function), never as a side effect of rendering
the UI. Streamlit reruns the whole script on every interaction; rendering
code must never itself write a history record, or a single user action can
produce duplicate rows. See `docs/AGENT_INSTRUCTIONS.md`.

## 13. Photos

Every recipe may have one photo.

- photos are stored on the local filesystem (not as DB blobs)
- the database stores a path/reference only
- photos are excluded from Git (`.gitignore`)
- photos should be resized/compressed on upload where practical
- filenames should be based on the stable recipe ID (e.g.
  `photos/<recipe_id>.jpg`), not the recipe's display name

Never commit household photos to GitHub.

## 14. Main User Interface

Target screens (built incrementally across milestones — not all exist yet):

**Home** — current week plan at a glance (7 days, one line each), quick link
into each day, "generate new plan" action.

**Recipes** — browsing interface, visual cards (photo, name, cook time,
enjoyment rating, seasonality). Filters: search, season, quick-fallback
only.

**Add/Edit Recipe** — friendly form:
1. photo
2. name
3. cook time
4. family enjoyment
5. seasonality
6. quick-fallback flag
7. servings
8. ingredients (structured, repeatable rows)
9. instructions
10. notes

**Weekly Calendar Input** — 7-day form: busy toggle + dinner-ready time
(default 6:00 PM) per day.

**Week Plan** — 7 days, each clickable into its recipe. Each day has a swap
action.

**Day/Recipe Detail** — photo, name, cook time, enjoyment, seasonality,
ingredients, instructions, notes, swap action.

**Grocery List** — generated, grouped-by-category, read-only view for the
current week plan.

## 15. AI Assist (Optional, Local)

The app may optionally integrate a locally-run model (e.g. via Ollama) for a
small set of assistive features. This integration must be **optional and
non-blocking** — the app is fully usable with it disabled or unreachable;
features relying on it simply don't appear or fail gracefully.

In scope:

- **Recipe import** — given pasted recipe text (or a pasted URL's fetched
  text), extract a structured draft: name, servings, cook time estimate,
  ingredient lines (name/quantity/unit), and instructions. The result is
  presented as a pre-filled Add Recipe form for the user to review and
  confirm — never saved automatically without review.
- **Ingredient categorization** — when a new ingredient line is added,
  suggest its `store_category` (produce, dairy, meat, pantry, frozen,
  other) automatically. The user can override the suggestion.
- **Swap suggestions with intent** — when swapping a day's recipe, allow a
  free-text hint (e.g. "vegetarian," "quicker," "use up the broccoli") and
  let the assist narrow candidate recipes accordingly, on top of the
  normal weighting in §9.
- **Shortcut suggestions** — for a given recipe or day, suggest simple
  effort-saving substitutions (e.g. "use frozen chopped veg instead of
  fresh," "pre-minced garlic") as optional text shown alongside the
  recipe, not stored as a permanent change to the recipe itself.

Out of scope: generating entirely new recipes from nothing, nutrition/
calorie analysis, and anything that writes to the database without the user
reviewing/confirming the result first.

Architecture: implemented as a separate, isolated service module (see
`docs/DATA_MODEL.md`), called only when the relevant screen is used. No core
screen (recipes, plan generation, grocery list) depends on this module being
available.

## 16. Database Model

Relational SQLite design. See `docs/DATA_MODEL.md` for full column-level
detail. Conceptual tables: `RECIPES`, `RECIPE_INGREDIENTS`, `WEEK_PLANS`,
`PLAN_DAYS`, `COOK_HISTORY`. Exact implementation (column types, indexes)
may vary, but these concepts and their separation of concerns must remain.
